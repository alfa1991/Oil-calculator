## 3. Обязательные проверки alpha

| ID | Сценарий | Условие приёмки |
|---|---|---|
| A-01 | Первый запуск в авиарежиме | Каталог, справочник, выпущенные расчёты, история и экспорт работают; нет login gate |
| A-02 | Изменение входа быстрым набором | Результат относится к последней полной валидной ревизии; незавершённый ввод не показывает старое число как текущее |
| A-03 | Пустое/0/отрицательное/очень большое значение | Метод возвращает предусмотренную ошибку или допустимое число; NaN/Infinity не выводятся |
| A-04 | мм↔м; bar↔МПа↔psi; atm↔at | Результат одинаков в пределах численного допуска; смысл единицы показан |
| A-05 | MD/TVD; absolute/gauge; ppm/mg/L | Различия явно заданы; недостающие условия не подставляются автоматически |
| A-06 | Эталоны каждой методики | Прямой результат, границы, недопустимые входы, обратные решения если есть; независимый эталон и версия |
| A-07 | RU decimal comma / EN decimal point | Правильная нормализация, неоднозначный ввод требует исправления |

| A-09 | Hide/reorder/favorites/new module | Настройки сохраняются и переживают миграцию; скрытое можно восстановить |

## 4. Допуск стабильной производственной версии

- Все активные методики имеют заполненный паспорт и approved_for_release; кандидат не попадает в производственный каталог.
- Для каждой есть независимый эталон, документированная численная погрешность и границы. Повторение той же функции в тесте не является независимой проверкой.
- Тестовые данные синтетические либо разрешённые/обезличенные; никаких фактических конфиденциальных скважин в GitHub.
- Пройдены проверки Android/iOS, хранения, миграций, экспорта и доступности; результаты фиксируются с устройством, ОС и commit SHA.
- Нет нерешённых критических ошибок вычисления, потери данных и высоких/критических уязвимостей в активных функциях. Низкий coverage не оправдывается количеством тестов; числовое покрытие не заменяет сценарии риска.
- Пользователь видит модель/ограничения и источник; обучение по типичным ошибкам ввода доступно без сети.
- Есть процедура сообщения об ошибке, исправления/отзыва метода и выявления затронутой истории.
- Подготовлены privacy/support/store декларации, права на справочные материалы, подпись и инструкции воспроизводимой сборки.
- При аккаунте/синхронизации выполнены проверки двух пользователей, E2EE, конфликтов, logout, удаления, восстановления ключа/копии и режима без связи.
- Заявления магазина не обещают безопасность и точность шире, чем доказано испытаниями. Статус внутренней проверки не называется сертификацией.

Если процедура работодателя требует утверждённой методики/проверки специалистом, самостоятельный расчёт в приложении не заменяет её. Кто и по какой процедуре подтверждает применение на объекте, определяется до такого использования.

## 5. Версионирование и управление изменениями

ТЗ spec-v0.1.0; приложение v0.1.0-alpha.1 далее vMAJOR.MINOR.PATCH; методика ID@version; БД schema_version; справочник reference_revision; набор эталонов fixtures_version. Build number монотонно возрастает в рамках платформы; нельзя путать его с SemVer.

MAJOR меняет несовместимый контракт, MINOR добавляет совместимую функцию, PATCH исправляет совместимую ошибку. Для результата расчёта даже исправление константы повышает версию методики; журнал содержит affected methods и migration/recalculation impact. Изменение UI не требует смены версии формулы, если алгоритм и данные неизменны.

Работа через короткие ветки и проверяемые commits/PR; production release после тестов. Не переносить экспериментальный метод в main как подтверждённый только по успешной CI. Формат предлагаемой задачи: ID, проблема, источник, целевая версия, критерии, риски, зависимости, evidence. Комментарии и PR не публикуются автоматически без отдельного поручения; документы и коммиты в указанный репозиторий разрешены запросом заказчика.
