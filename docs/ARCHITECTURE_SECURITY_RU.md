# Архитектура, сервер и безопасность — 0.1.0

Статус: проектные решения. Ни одна настройка безопасности пока не реализована и не испытана.

## 1. Общая кодовая база

Предлагается Flutter/Dart для Android и iOS: одна реализация ядра и интерфейса, отдельные подписанные пакеты. Это рекомендация для ограниченных ресурсов, а не гарантированное преимущество без прототипа. Минимальные версии ОС и Flutter закрепляются после проверки доступных устройств и зависимостей. Рассмотреть Android 9+/iOS 15+ как первоначальные кандидаты, не объявлять поддержку до сверки с выбранным SDK.

| Слой/каталог | Ответственность |
|---|---|
| packages/calculation_core | Чистое типизированное ядро, единицы, валидация, версии и паспорта методик; без Flutter/сети |
| lib/features/calculators | Общая форма и представление результата; отдельные специализированные компоненты при необходимости |
| lib/features/catalog | Реестр, поиск, избранное и пользовательская видимость |
| lib/features/wells | Карточки и конфигурации скважин |
| lib/features/history | Неизменяемые снимки расчётов |
| lib/features/reference | Проверенный автономный справочник |
| lib/features/export | Локальный PDF/XLSX, очистка временных файлов |
| lib/features/settings | Темы, доступность, единицы, язык, календарь и пояс |
| lib/data/local | Зашифрованная БД, транзакции и миграции |
| lib/data/sync | Очередь, конфликты, шифрование, перенос между устройствами |
| lib/integrations | Auth, региональные магазины, поддержка/реклама; отключаемые адаптеры |
| docs / test / integration_test | Паспорта, источники, эталоны, проверки ядра и пользовательских сценариев |

Навигация знает стабильные ID, а не формулы. Реестр задаёт параметры формы, а вычисление выполняет закреплённый типизированный модуль. Не использовать eval, интерпретацию произвольных выражений или скачиваемые скрипты для производственного расчёта.

## 2. Локальное хранение

SQLite хранит wells, well_sections, well_properties, calculation_snapshots, favorites, hidden_items, preferences, schema_migrations и после включения синхронизации sync_queue/object_revisions/deletion_tombstones. Локальные ID UUID, принадлежность аккаунту отдельно. Значения имеют quantity_kind, unit_id, canonical_value и оригинальный ввод. Для давления сохраняется reference_kind; для глубины depth_kind; для расхода conditions_basis.

В calculation_snapshot входят formula_id, formula_version, core_version, app_version, input_revision, inputs, assumptions, result, warning_codes, source_revision, well_revision, UTC time, zone_id, offset, locale/calendar. Для чисел при сериализации используют проверенный обратимый формат; исходная строка не используется как доверенное число.

Изменение карточки, массовая миграция и запись истории транзакционны. Перед миграцией есть восстанавливаемая зашифрованная копия; failure не оставляет половину схемы. Не хранить расчёты в открытых logs/preferences. Защита БД выбирается с проверкой Android/iOS и лицензии, а не только по наличию слова encryption у библиотеки.

Ключ локальной БД защищается Android Keystore / Apple Keychain. Режим биометрии и правила изменения системного кода/биометрии проверяются; утрата ключа не маскируется как пустая БД. Возможность резервного копирования без аккаунта предусматривается отдельным зашифрованным архивом с предупреждением о восстановлении и сроках.

## 3. Что использовать как сервер

Первая alpha полностью локальная: сервер не нужен. Для конечного аккаунта и синхронизации рекомендуемая схема: **API + PostgreSQL + хранилище зашифрованных объектов**, у выбранного провайдера. Владельцем сервиса выступает владелец приложения; БД находится в его облачном проекте/VPS, не в GitHub и не в телефоне разработчика.

| Вариант | Преимущества | Издержки/условия |
|---|---|---|
| Managed Supabase | PostgreSQL/Auth, готовые средства разграничения доступа | Проверить доступность региона для владельца, условия обработки, квоты и дальнейшие расходы; бесплатный тариф не обещает SLA |
| Self-hosted Supabase | Контроль региона и инфраструктуры | Администрирование, обновления, SMTP, резервные копии, мониторинг; VPS не становится бесплатным |
| FastAPI + PostgreSQL на управляемом российском хостинге/VPS | Контроль API, расположения и состава данных | Больше самостоятельной работы: Auth, лимиты, очереди, удаление, резервные копии, эксплуатация |

Для регистрации владельца в России и потенциальных персональных данных российских граждан предпочтительно начать подбор с российского региона размещения; конкретный провайдер не назначен. До включения сервиса проверить применимые требования локализации/уведомлений/трансграничной передачи по официальным источникам и фактической схеме обработки. Это открытая задача перед запуском, а не готовое юридическое заключение. Международные условия требуют отдельной проверки. Не делать автоматическое распределение данных по стране языка пользователя.

При нулевом бюджете безопасный первый этап — локальные функции. Пробный бесплатный сервер пригоден для непроизводственных тестовых данных; запуск конфиденциальной синхронизации требует реальных резервных копий, проверки защиты и понятной стоимости эксплуатации.

## 4. Синхронизация и шифрование

Производственные объекты шифруются на устройстве проверенной библиотекой AEAD, например AES-GCM или XChaCha20-Poly1305. Собственная криптография не разрабатывается. К каждому объекту привязываются через authenticated data ID/версия/тип; nonce не повторяется при одном ключе. Сервер хранит ciphertext, nonce, версию формата и служебные данные, не открытое содержимое.

Локальный ключ БД и ключ облачного шифрования имеют отдельные назначение/ротацию. Первоначальное добавление второго устройства — через подтверждённое устройство либо recovery secret. Рекомендуется recovery key, который пользователь хранит отдельно; пароль аккаунта и ключ восстановления не смешиваются. Сброс пароля аккаунта не должен обещать восстановление зашифрованных данных без ключа. Утрата всех ключей означает невозможность расшифрования; это поясняется до активации и проверяется сценарием восстановления.

Auth предпочтительно сначала email/пароль или email-ссылка по результатам региональной проверки SMTP; не обещать бесплатную доставку/защиту от злоупотреблений. Пароли на сервере обрабатывает проверенный Auth-провайдер/библиотека; не хранить открытый пароль. Если добавлены социальные входы, отдельно проверить требования Apple к альтернативному входу.

Изоляция пользователей обязательна на API и БД. Для Supabase включить RLS и ограничения owner_id; тестировать read/write/delete другого пользователя и anon. Привилегированный service key никогда не передаётся приложению. В E2EE доступ к чужому ciphertext также является уязвимостью.

Очередь имеет стабильные operation IDs, backoff, ограничение размера, явный статус последней успешной операции. Конфликты используют серверные ревизии, не клиентское время. Удаление и восстановление из копий согласованы с retention. После logout явно спросить действие с локальными облачными копиями, сохраняя автономные возможности и доступность экспорта.

## 5. Границы конфиденциальности

| Категория | По умолчанию | При включении сервиса |
|---|---|---|
| Ввод и результаты | Только на устройстве | Выбранные объекты в зашифрованном виде |
| Названия скважин/месторождений, заметки | Только на устройстве | Внутри ciphertext |
| Email/ID аккаунта | Не требуются | Auth/БД учётных записей |
| IP, время запросов, размеры объектов | Нет фонового API | Видны инфраструктуре; минимизировать и установить сроки хранения |
| Crash-логи | Не отправляются автоматически | Только добровольный очищенный отчёт, без секретов и введённых значений |
| Реклама | Отсутствует на первом этапе | Выбранный регион/язык, без карточек и расчётных данных |

Сквозное шифрование не скрывает всю метаинформацию и не делает регистрацию «без обработки персональных данных». Политика конфиденциальности должна точно описывать действующее приложение и каждый сторонний SDK.

## 6. Проверки безопасности

| Угроза | Контроль | Доказательство |
|---|---|---|
| Доступ к БД потерянного телефона | Зашифрованная БД, защищённый ключ, опциональный lock | Проверка файлов и ключей, сценарии блокировки/восстановления |
| Подмена данных в сети | TLS и AEAD | Негативный тест сертификата и изменённого ciphertext |
| Доступ к другому аккаунту | Изоляция API/RLS | Два аккаунта: чужие ID, списки, read/update/delete |
| Утечка через журнал/диагностику | Редакция и allowlist полей | Инспекция логов/пакетов с уникальными контрольными строками |
| Утечка через резервную копию | Явная политика БД/ключей | Backup→restore на устройстве и проверка содержимого |
| Секреты в репозитории/пакете | Secret scan, server-only keys | Скан исходников и release APK/IPA |
| Вредоносная зависимость | Закрепление версий, SBOM, анализ advisory | Отчёт и журнал рассмотренных исключений |
| Подмена методики | Формулы в подписанной сборке, проверка справочных пакетов | Тест повреждённого/старого пакета и номера версии |
| Потеря данных при sync/миграции | Транзакции, ревизии, конфликтные копии | Обрыв процесса/сети, повтор операции, downgrade handling |
| Утечка XLSX/Excel injection | Текстовые типы, безопасная передача | Тест опасных строк и временных файлов |

Перед выпуском: модель угроз, сопоставление MASVS/MASTG, static scan, dependency scan, secret scan, release-сборка без debug, сетевой аудит, тесты local storage/export, тесты auth/RLS при наличии сервера. Обфускация полезна только как дополнительная мера; она не хранит секрет безопасно.

Критические и высокие нерешённые уязвимости в активных функциях блокируют выпуск. Полный независимый penetration test не объявляется выполненным по наличию автоматического сканера. На первом этапе допустимо не подключать сервер/рекламу/платежи, пока их проверки не выполнены.
